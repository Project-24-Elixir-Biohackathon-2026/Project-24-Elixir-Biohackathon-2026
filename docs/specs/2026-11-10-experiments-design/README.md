# Experiments: threat, mitigation, tests and results, end to end in a workspace

Status: draft (fork PR #84). Latest clarification: none.

**Who reads it.** Whoever plans or builds the slices; reviewers of an experiment PR; maintainers of the Coder
template (`platform/coder/`), the evaluations (`platform/promptfoo-evals/`) and the instance (`platform/instance/`).

**The problem.** The parts of an evaluation exist, but only a maintainer can put them together, by hand, from
their own controller. A threat is a file in `threats/`; the routes a canary takes (paths P1–P4) and the controls
that close them (the `spe_harden_*` switches) live only in a design text and in Ansible variables; the test labels
are a fixed set in `matrix.py`; `run.sh` runs only where the instance's hand-off is (the controller); results are
read with `promptfoo view` on a laptop. A participant in a portal workspace can change the stack (`spe-apply`) and
chat with the agent, but cannot pick a hardened build, run the suite, see its results, or contribute a mitigation
that others can rebuild and measure.

**The decision.** An **experiment** is a file (`experiments/<name>.yml`, also a Coder preset) plus the files it
names: a threat, the paths it takes, a mitigation written as a switch, and tests. A new Coder template,
`spe-experiments`, reads mitigations and experiments from files, so contributing one adds options without editing
Terraform; the existing template `spe` stays as it is. In the workspace, `spe-eval run` measures
the experiment on the workspace's own VM: the suite with the mitigation off (baseline), then on (mitigated), same
build and canaries; a read-only `promptfoo view` behind an "Evaluations" app shows both. A contribution is a PR
of those files, gated by `check_experiment.py` and carrying its result. Most participants will do all of it
through a coding agent, so every step is a command with text output. The canary ladder is the first set of
experiments, built through exactly this structure.

| 1 | An experiment is a file `experiments/<name>.yml` (also the new template's preset) with an `experiment:` block naming one threat, its paths, the mitigation under test (or none: a one-arm experiment such as `ladder-l0`), the base mitigations, its planted injections and its tests; the code it names lives in the repo | [01](01-experiment-model.md) | `check_experiment.py ladder-l1` and `ladder-l0` pass; an experiment naming an unknown threat, path, mitigation or test id fails it with that id in the message |
| 2 | Paths and mitigations are files like threats: `paths/P<n>-<slug>.md`, `mitigations/<id>.yml`; `validate.py` checks all three | [01](01-experiment-model.md) | `validate.py` passes on P1–P4 and L1–L3; a path without its front matter keys, or a mitigation whose `off` differs from the Ansible default, fails it |
| 3 | The test labels' value sets are read from those files, not listed in code: `threat` from `threats/`, `path` from `paths/`, `closed_by` from `mitigations/`; `group` from the test files' names | [01](01-experiment-model.md) | `tests/test_catalogue.py` passes with `matrix.CATALOGUE` built from the files; adding `paths/P5-x.md` makes `path: P5` valid with no code change; `matrix.py counts` on the committed ladder results is unchanged |
| 4 | A mitigation declares its Ansible values when on and when off; off is the default, so a build without it is today's; each Ansible key is owned by one mitigation, so any set of mitigations merges without one silently overriding another | [01](01-experiment-model.md) | `check_experiment.py` refuses a mitigation whose `off` values differ from `group_vars/all.yml`, and `validate.py` refuses two mitigations whose `on` set the same key, naming both; a workspace with no mitigation selected builds the same `ansible_vars` as today (a Terraform plan diff of zero for those keys) |

| 7 | Evaluations of an experiment run on the workspace VM, from the clone in `~/sperange`, by `spe-eval`, for any experiment in the clone whose creation-time values match the build (a participant's new one, written in a workspace created from `ladder-l0`); the controller-side `run.sh` route stays for official ladder runs | [03](03-evaluation-in-workspace.md) | in a workspace from `ladder-l0`, an experiment made with `spe-eval new x --from ladder-l0` (uncommitted) runs with `spe-eval run x`; one whose creation-time `vars` or `parameters` differ is refused with the differing keys (`experiment`, `mitigations` and `seed` are not compared) |
| 8 | Create writes a VM-local hand-off into `~/spe-eval/handoff/` (mode 0700, the workspace user): every file the suites read, with an SSH-less `hosts.yml` whose paths are VM-local, so `isolation.py`, the probes and the asserts run locally; mounted into no container | [03](03-evaluation-in-workspace.md) | `isolation.py exists/snapshot/restore` work on the VM with no SSH; the utility group's asserts find `trs-installed.json` and `drs-inventory.json` there; `docker inspect` of every container on the VM shows no mount containing `~/spe-eval/handoff` or `instances/local.yml` |
| 9 | `spe-eval run` measures two arms: exactly the base mitigations (baseline), then base plus the mitigation under test (mitigated), every other mitigation off, each applied with `spe-apply all` and each with its own isolation snapshot; an experiment without a mitigation under test has the baseline arm only | [03](03-evaluation-in-workspace.md) | the snapshot key includes the arm's mitigation set, and taking one arm's snapshot leaves the other's in place (isolation tests); a mitigation selected on the form but outside the experiment is off in both arms; `spe-eval run ladder-l0` gives one arm, `baseline`; after a run, the stack is left in the arm the workspace was built with |

| 11 | One `spe-eval` run or `arm` at a time per VM (a lock), and `spe-apply` refuses while it is held, except when called by the holder (the lock's token in its environment) | [03](03-evaluation-in-workspace.md) | unit tests of `spe-eval`: a second `spe-eval run`, an `arm` and a plain `spe-apply` all refuse while the lock is held; `spe-apply` with the holder's token proceeds |

**Early output.** One workspace on de.NBI from `ladder-l1`, one `spe-eval run --repeat 1`, and the Evaluations
app showing the baseline (L0) and mitigated (L1) evals side by side. The user looks at it: whether the two arms
read as one comparison in promptfoo's UI, and whether a run started by a coding agent from the workspace guide's first steps (slice 3) is a flow a participant
could follow alone. What would change a decision: an unreadable comparison changes 10 and 14 (eval naming, or a summary page of
our own); a run too long or confusing for a participant changes 9 and 16 (fewer tests per arm, the guide's steps, `status` output).
It needs slices 1–4 (*Inputs for the plan*); slice 2's create form is the smaller sample before it.

## Glossary

| Term | Meaning |
|---|---|
| **Threat** | A class of harm, `threats/TM-NNN-*.md` |
| **Path** | A route by which a canary reaches the agent or leaves the SPE, `paths/P<n>-*.md` |
| **Mitigation** | A control that closes or narrows paths, written as Ansible values when on and off, `mitigations/<id>.yml` |
| **Experiment** | `experiments/<name>.yml`: one threat, its paths, one mitigation under test, base mitigations, tests; also a preset of `spe-experiments` |
| **Testbed** | A preset of the existing template `spe`, `platform/coder/template/testbeds/<name>.yml` (unchanged) |
| **Arm** | One of an experiment's two builds: **baseline** (base mitigations) or **mitigated** (base plus the one under test) |
| **Hand-off** | The instance's files the evaluations read: `canaries.json`, `hardening.json`, `injections.json`, `trs-installed.json`, `drs-inventory.json`, `ca.crt`, `hosts.yml`, `agent_api_key` |
| **Ladder** | The experiments `ladder-l0` … `ladder-l3`, each adding one level's mitigation |
